# Decisions

Decisions made during the build where `docs/PLAN.md` was silent. One line
each, dated.

- 2026-09-17 — Node 22.22 LTS is the local toolchain (Node 20 is not installed); CI pins Node 20 and `engines` requires `>=20`, so both are supported.
- 2026-09-17 — Rust edition 2024 and workspace `rust-version = 1.88` (the floor set by `keyring` 4 and `zip` 8).
- 2026-09-17 — TypeScript 6.0 rather than 7.0: `typescript-eslint` supports `<6.1`.
- 2026-09-17 — Clippy allow-list: `module_name_repetitions` (types such as `SvnError` inside `svn` read better than the alternative), `missing_errors_doc` (every error is a typed enum with a stable code documented on the enum), `must_use_candidate` (noise on plain getters). `unwrap_used`, `expect_used` and `panic` are warnings, promoted to errors by `-D warnings`, and allowed only in tests via `clippy.toml`.
- 2026-09-17 — The theme choice persists in the webview's `localStorage` so it applies before first paint with no flash; it is a UI preference, not app state.
- 2026-09-17 — Navigation lists all five screens; Release shows an empty state until a project is opened from Projects.
- 2026-09-17 — Generated TypeScript bindings live in `apps/desktop/src/ipc/bindings/` (git-ignored) via `TS_RS_EXPORT_DIR` in `.cargo/config.toml`; `npm run typecheck` and `npm test` regenerate them with `cargo test export_bindings`.
- 2026-09-17 — App icons are rendered once from `icons/source.svg` with `cargo tauri icon` and committed, because the bundler needs them at build time; only desktop sizes are kept.
- 2026-09-17 — `cargo deny` checks `unmaintained` for direct dependencies only; the flagged crates (`unic-*`, `proc-macro-error`) are deep in the Tauri and GTK tree.
- 2026-09-17 — App identifier `com.degird.svnpush`.
- 2026-09-17 — "Installers build on all three platforms" (M0) is verified locally for Windows (NSIS and MSI); macOS and Linux are built by the `build` workflow, which cannot run from this machine.
- 2026-09-17 — Crates added for M1: `thiserror` (typed errors with stable codes, plan §4), `serde`/`serde_json` (DTOs and config files), `regex` (header scanning and user-configured version locations), `semver` (version ordering with normalisation), `ts-rs` (DTO types for the UI, plan §14.2); dev-only `proptest` (round-trip properties, plan §15) and `tempfile` (filesystem tests).
- 2026-09-17 — Errors that reach the UI implement one `Coded` trait (`code()` plus optional `fix()`); the shell turns any of them into a single `{ code, message, fix }` DTO.
- 2026-09-17 — File changes are composed in an in-memory `EditSet` before anything is written, because two sources can edit the same file (a version constant inside the main plugin file) and the diff, snapshot and journal all need the before/after pair.
- 2026-09-17 — `Readme.headers` is an ordered list with line numbers rather than a map, so fixes can name the line; lookups are case-insensitive.
- 2026-09-17 — `PluginFacts.readme` is optional: a plugin without `readme.txt` still detects, and V05/V10 report the missing file.
- 2026-09-17 — The readme parser reads the WordPress.org `=`-heading syntax only (`=== Name ===`, `== Section ==`, `= Entry =`); Markdown-style `##` readmes are not parsed in 1.0.
- 2026-09-17 — Writing a changelog entry for a version that already has one replaces that entry's body and keeps its title (for example a date), instead of adding a duplicate. A missing `== Changelog ==` section is appended at the end; a missing `== Upgrade Notice ==` is created directly after the changelog when the draft has a notice.
- 2026-09-17 — Version sources with no value are reported as empty rather than skipped, so V01 names them; a missing readme contributes no readme sources. A custom location that matches more than once yields one source per match.
- 2026-09-17 — Slugs are lowercase letters, digits and hyphens (the WordPress.org rule); the slug is the SVN URL's last segment, ignoring a trailing `/trunk`.
- 2026-09-17 — Git facts and the previous released version are added to `PluginFacts` by the run (M4), because they need the `tools` and `svn` modules (M3); `detect` itself stays a pure local-disk read.
- 2026-09-17 — The real-world fixture copies AuthDock's `readme.txt` and lines 1–28 of `authdock.php` (the header block and its `ABSPATH` guard, so V09 has a real example).
- 2026-09-17 — `fixtures/**` is marked `-text` in `.gitattributes` so byte-exact inputs (line endings, BOM) are never normalised by git.
- 2026-09-17 — Crates added for M2: `ignore` (gitignore semantics for `.distignore`, plan §7.1), `walkdir` (follows symlinks and reports loops, already a dependency of `ignore`), `blake3` (content hashes, plan §7.4), `zip` with only the `deflate-flate2-zlib-rs` feature (the package zip), `sha2` (the `.zip.sha256` checksum).
- 2026-09-17 — rustfmt uses `use_small_heuristics = "Max"` so short expressions stay on one line.
- 2026-09-17 — Integration test files allow `unwrap`/`expect`/`panic` at file level; clippy's `allow-*-in-tests` covers only `#[test]` functions, not their helpers.
- 2026-09-17 — The hard-excluded list matches case-insensitively (`Thumbs.db`, `*.ZIP`); `.distignore` keeps git's case-sensitive semantics.
- 2026-09-17 — The zip holds explicit directory entries (`<slug>/`, `<slug>/includes/`) alongside files, all sorted, with the zip epoch timestamp and fixed permissions, so the same tree always produces the same SHA-256.
- 2026-09-17 — The `.zip.sha256` file uses the `sha256sum` format (`<hex>  <name>`) so `sha256sum -c` verifies it.
- 2026-09-17 — V12 treats `.zip .tar .gz .tgz .rar .7z` as archives and `.exe .dll .msi` as executables; `.phar` is blocked unless the project allows it.
- 2026-09-17 — V09 accepts a `defined( 'ABSPATH' )` or `defined( 'WPINC' )` check anywhere in the main file (whitespace-insensitive).
- 2026-09-17 — Checks that cannot run yet report Skip with the reason: V13 before Build creates the zip, V15 before Preview creates the working copy. Skip never blocks; Build and Preview re-run them.
- 2026-09-17 — W02 compares major.minor only, the precision WordPress.org uses for "Tested up to".
- 2026-09-17 — Source paths longer than 260 characters are listed on the package (`long_paths`) and shown in Build as a notice, not as an eleventh warning.
- 2026-09-17 — Builds are pruned to the three most recently modified version folders per plugin.
- 2026-09-17 — Crates added for M3: `tokio` (`process`, `io-util`, `time`, `sync`, `macros`, `rt`; async child processes with streamed output, plan §4), `tokio-util` (the `CancellationToken` the plan names), `roxmltree` (read-only parsing of `svn status --xml`, avoiding fragile column parsing).
- 2026-09-17 — The 60-second network timeout (plan §12.2) is Subversion's own `servers:global:http-timeout=60`, passed with `--config-option` on every server call: it bounds a silent connection without cutting off a long but progressing commit. Cancellation kills the child process.
- 2026-09-17 — `svn` runs with `LC_MESSAGES=C` and `LANGUAGE=C` (English messages) but without overriding `LC_ALL`/`LC_CTYPE`, so non-ASCII file names keep working; errors are classified by Subversion's locale-independent `E` codes.
- 2026-09-17 — Server calls always pass `--no-auth-cache`, and `--username`/`--password-from-stdin` when credentials are given; `svn add` passes `--no-auto-props --no-ignore` so a user's global auto-props never set `svn:eol-style` and global ignores never silently drop a packaged file.
- 2026-09-17 — Paths are passed to `svn add/delete/propset` in batches of 100 to stay far below command-line length limits, instead of a `--targets` temp file inside the working copy.
- 2026-09-17 — `tag` refuses when `tags/<version>` already exists (`SVN_TAG_EXISTS`): the integration suite showed `svn copy` into an existing folder nests the copy (`tags/1.0.0/trunk`) instead of failing. The copy is pinned to the recorded trunk revision (`trunk@REV`).
- 2026-09-17 — Tag verification retries three times ten seconds apart (thirty seconds) before reporting "published, unverified".
- 2026-09-17 — The dry-run revert also deletes unversioned files the sync left behind, because `svn revert` keeps added files on disk.
- 2026-09-17 — The `Secret` type has redacted `Debug`/`Display`, no `Clone` and no `Serialize`; it does not claim to zero memory on drop, which the compiler may optimise away.
- 2026-09-17 — The `svn-integration` CI job runs on Linux and macOS, where Subversion installs from the package manager in seconds; Windows runs the suite locally.
- 2026-09-17 — Crates added for M4: `similar` (unified diffs for Step 3, plan §3), `keyring` 4 with its default `v1` stores (Windows Credential Manager, macOS Keychain, Secret Service); the shell adds `tauri-plugin-dialog` (the folder picker) and `tauri-plugin-opener` (open the WordPress.org plugin page, reveal the zip). No date library: UTC timestamps are formatted in a 20-line `clock` module.
- 2026-09-17 — `rust-version` is 1.89 for `File::try_lock`, which gives the per-project lock (plan §10) an operating system file lock that a crashed app never leaves stale.
- 2026-09-17 — Detect, Write and the version/readme checks work on the project folder (the sources); Build packages the package root, which a pre-build command may create. When the package root does not exist yet, V10–V12 in Step 4 report Skip and run in Build against the staged tree.
- 2026-09-17 — The `vault` core module (keychain get/set/delete, `accounts.json` for SVN account names) is built in M4 rather than M5, because M4's publish step needs credentials; the Vault screen and Test remain M5.
- 2026-09-17 — A dry run reports V16 (credentials) as Skip: it never commits, so it can rehearse a release before an account is set up.
- 2026-09-17 — A dry run restores the Step 3 snapshot at the end as well as reverting the working copy, so a rehearsal leaves the plugin's files byte-for-byte unchanged; the diffs stay in the report.
- 2026-09-17 — The change set compares the last git tag with the working tree (uncommitted edits ship, so they count) plus untracked files; without git or without a tag it compares the package root with the trunk working copy, checking the working copy out anonymously first. Identical trees stop the run with "nothing to release".
- 2026-09-17 — The draft is pre-filled with the header version when it is already newer than the previous release (the developer bumped it by hand), otherwise the next patch; the changelog is pre-filled from an entry already written for that version, else the commit subjects as a list.
- 2026-09-17 — Resume after an interruption before the trunk commit rolls the run back (snapshot and working copy) and starts a fresh run; Resume after a trunk commit creates only the tag. Discard marks the journal `discarded` so it stops being offered.
- 2026-09-17 — The UI receives the whole `RunState` after every change (plus separate log-line events) and renders it; the store keeps the newest 2,000 log lines per project.
- 2026-09-17 — Per-file SVN diffs are captured into the preview when Step 6 runs (capped at 2 MB in total) instead of being fetched on click, because a dry run reverts the working copy before the developer reads the report.
- 2026-09-17 — App commands are listed in `build.rs`'s app manifest so each gets an `allow-<command>` permission; the default capability grants those, event listen/unlisten, the folder dialog, opening `https://wordpress.org/plugins/*` and revealing a file, and nothing else.
- 2026-09-17 — Shell logic lives in `service/` as plain functions over `AppState` so it is unit-tested without a window; `commands.rs` only forwards arguments.
- 2026-09-17 — The real-window verification drives the running app through WebView2's remote debugging port with `playwright-core` installed in a scratch folder (not a project dependency); the project is added through the `add_project` command because a native folder dialog cannot be scripted.
- 2026-09-17 — M4's "real publish of a throwaway plugin" is verified against a local `file://` repository once the Vault screen exists (M5): there is no throwaway WordPress.org plugin or committer account available to this build.
- 2026-09-17 — M5 builds the parts of the AI layer the Providers screen cannot work without: the provider contract, all ten adapters, the registry and order, the HTTP client and provider records (plan §9.1–9.4, 9.6). M6 adds prompts, schemas, the router, the mock-server lifecycle tests and the Draft step wiring. The Providers screen is "driven entirely by each adapter's AdapterMeta", and Test, ↻ and the fleet line need a working client.
- 2026-09-17 — Crates added for M5: `reqwest` (the AI HTTP client, plan §3; rustls, JSON, HTTP/2, system proxy only), `ulid` (`prov_<ulid>` ids, plan §9.6), `tracing` (plan §14.1); the shell adds `tracing-subscriber` (fmt only), `tracing-appender` (daily files, seven kept) and `tauri-plugin-updater` (plan §3).
- 2026-09-17 — Default model ids, checked against each vendor's documentation today (plan §19.2): Gemini `gemini-3.8-flash`, Claude `claude-sonnet-5`, OpenAI `gpt-6-astra`, OpenRouter `anthropic/claude-sonnet-5`. They are record settings, not code.
- 2026-09-17 — Gemini JSON answers use `responseMimeType` plus `responseJsonSchema` (standard JSON Schema) rather than `responseSchema` (Google's OpenAPI subset), so one schema serves every dialect.
- 2026-09-17 — OpenAI requests send `max_completion_tokens` (OpenAI deprecated `max_tokens`); the other compatible providers keep `max_tokens`, which their servers read. No adapter sends a temperature: SVNpush never sets one, and current Claude models reject sampling parameters.
- 2026-09-17 — OpenRouter attribution headers are `HTTP-Referer: https://github.com/FlyToRakib/svnpush` and `X-OpenRouter-Title: SVNpush`, as documented by OpenRouter.
- 2026-09-17 — Client timeouts: 30 s for Revoye submit, poll, cancel, model list and status calls (plan §9.4); 180 s for a synchronous model answer, which can take minutes to write. The poll loop is bounded by the adapter's `max_ms`.
- 2026-09-17 — `AiClient::with_url_rewrite` lets tests point a fixed-endpoint adapter (Revoye) at a mock server; the adapters still build their real URLs.
- 2026-09-17 — Provider Test for Revoye calls `GET /v1/status`, which proves the key and reports the fleet without taking an agent's time; every other provider answers a one-word prompt. A passing test clears "needs attention".
- 2026-09-17 — Vault Test reads the password back from the keychain and lists the server with it, and says plainly that WordPress.org only checks a committer's password on commit; there is no read-only way to verify it.
- 2026-09-17 — The model list loads silently when the API key field loses focus after a key is pasted (the field's `change`), as SyncDock's page does.
- 2026-09-17 — Log redaction removes anything shaped like an API key or bearer token (Revoye, Anthropic, OpenRouter, OpenAI, Google key formats and `Authorization`/`x-api-key` values) before a byte reaches the file; the same function cleans the diagnostics bundle.
- 2026-09-17 — The updater public key is compiled in; its private key was generated for this build and is not in the repository. Before the first signed release the owner must generate their own key pair (`cargo tauri signer generate`), replace `plugins.updater.pubkey`, and add the private key as the `TAURI_SIGNING_PRIVATE_KEY` CI secret (docs/RELEASE.md).
- 2026-09-17 — The M4 real publish was completed from the UI against a local `file://` repository (trunk r2, tag r3, verified), with the SVN password stored in the Windows Credential Manager through the Vault screen.
- 2026-09-17 — Crates added for M6: `jsonschema` (validates every AI answer, plan §9.7; default features off, so it never fetches remote `$ref`s) and `wiremock` as a dev-dependency (the mock-server lifecycle tests, plan §15).
- 2026-09-17 — The `explain_failures` fix object carries `original` (the exact readme text to replace) beside `replacement`: a replacement alone cannot be applied safely. A fix is offered only when its path is `readme.txt` and `original` occurs exactly once; everything else is shown as an explanation, never applied. Applying re-checks the text at that moment, adds the diff to Step 3's diffs and runs Verify again.
- 2026-09-17 — "Version-text fixes" from plan §9.7 are not applied from the explanation: every version source is written by Step 3 from the approved draft, so a wrong version is fixed by cancelling and approving a new draft, not by editing one file.
- 2026-09-17 — The failed-checks explanation starts automatically when a blocking check fails and a provider resolves; the run then waits in the new `AwaitingFixes` phase for Apply or Stop (Stop ends the run as `CHECKS_FAILED`, with rollback). With AI off or no provider the run fails straight away, as before.
- 2026-09-17 — Change material: one `git diff` against the last tag (untracked text files added as new-file diffs), or per-file diffs between the package root and the trunk working copy; ordered readme and PHP, then JS/TS/CSS, then the rest; each file cut at 20,000 characters. Above 60,000 characters in total, at most 25 files are summarised one by one and the rest are named only.
- 2026-09-17 — Default AI exclude patterns are `vendor/`, `node_modules/`, `*.min.js`, `*.min.css`, `*.map`, `*.lock` and `package-lock.json`. Files named `.env*`, `*.pem`, `*.key` or `wp-config.php` are withheld whatever the patterns say. Paths are matched with the `ignore` crate's gitignore rules.
- 2026-09-17 — The project AI setting is `Default`, `Pinned { provider_id }` or `Off`. It is machine-specific (provider record ids exist on one machine) and so ignored in `.svnpush.json`; the exclude patterns are shared.
- 2026-09-17 — The privacy notice is per provider record (`privacy_notice_seen` holds record ids) and appears before the first request that record would receive, in the Draft or Verify step. Declining writes the draft by hand.
- 2026-09-17 — A provider chosen with the Change link stays chosen for the rest of that run (the explanation uses it too); it is never saved to the project.
- 2026-09-17 — While the AI works the developer can still act: Approve uses the form as it is, Change restarts with another provider, and "Stop and write it myself" stops the request. Each stops the request first, which for Revoye deletes the queued job on the server.
- 2026-09-17 — An AI version that is invalid or not newer than the previous release is replaced with the next patch and the draft shows why (plan §12.4). A refusal (`Safety`) or a cut-off answer is not retried; a schema failure is retried once with the validation error, then shown as raw text.
- 2026-09-17 — The release summary is shown and editable in the draft form but written nowhere: plan §5.3 lists no destination for it. It is there to copy into an announcement.
- 2026-09-17 — M6's "real draft" verification ran in the real window against a local OpenAI-compatible stub server, not a real model: this machine has no Revoye, Gemini or other API key and no local model server, and installing one would mean downloading software. The window run covered a failing default provider, Change, the privacy notice, the draft, the explanation, an applied readme fix and a completed dry run. The request the stub received contained the diff and no credential. A real Revoye draft and a real Gemini draft remain for the owner to run.
- 2026-09-17 — The tauri-generated `permissions/autogenerated/*.toml` files are no longer committed: `build.rs` regenerates them from the command list on every build.
- 2026-09-17 — An assets-only release is a run mode, not a separate engine. Detect runs, Changes and draft, Write and Build are Skipped, Verify runs V14, V16 and W04 (the checks about committing and the assets themselves), and Preview adds V15, mirrors only `assets/` and stops with `NOTHING_TO_RELEASE` if the server already matches. Publish commits only `assets/` with one message. It ends in the Verified phase, shown as "Assets published". It records `revisions.assets`, and does not change the project's "last release", which describes versions.
- 2026-09-17 — Resuming an interrupted run that has no trunk commit starts a fresh run of the same kind (dry run or not, assets-only or not), rather than always a full release.
- 2026-09-17 — The one-time privacy notice is an inline panel in the AI section, which takes focus when it appears, not a dialog: plan §11.2 allows dialogs only for the Publish confirmation and destructive actions.
- 2026-09-17 — Accessibility pass: every colour token pair used for text meets WCAG AA (4.5:1) in both themes. Input, select and textarea borders use a new `--color-border-input` token that meets the 3:1 non-text minimum. Phase changes are announced through a visually hidden status region. Every control was reached with Tab in the running app, each with a visible focus ring. Side-by-side fields no longer inherit the stacked-field top margin.
- 2026-09-17 — Diagnostics export is the Settings "Copy diagnostics" action built in M5 (plan §6.3 and §11.1 call it Copy diagnostics). No file export was added.
- 2026-09-17 — The build workflow uses `tauri-apps/tauri-action@v1` (the current major in its README). It creates a draft release, uploads `latest.json` with the NSIS installer preferred for Windows updates, and signs updater artifacts from the `TAURI_SIGNING_PRIVATE_KEY` and `TAURI_SIGNING_PRIVATE_KEY_PASSWORD` secrets (names from the Tauri updater docs). Code signing stays off for 1.0, per plan §19.1.
- 2026-09-17 — README screenshots were taken from the running app with a demo plugin and a local `file://` repository under the git-ignored `target/demo/`, so no personal paths appear. The AI draft in them came from the local OpenAI-compatible stub used for M6 verification, configured as a "Local model" record.
- 2026-09-17 — The `svn-integration` CI workflow now runs the engine suite (`run_integration`) as well as the SVN suite; it had been running only the latter.
- 2026-09-17 — M7's "two external developers release a plugin with no help beyond the README" and the three-platform installer builds need people and CI runners this build does not have; they are listed in docs/BUILD-REPORT.md for the owner.
- 2026-09-17 — The git change set and diff use `git diff --relative`, and W01 strips `git rev-parse --show-prefix`, so a plugin folder inside a larger repository gets paths relative to the plugin (as untracked files already were); found while writing the build report.
- 2026-09-17 — Node 22 (22.22.2 or newer) is required locally and in CI: jsdom 30 and undici 8, used by the frontend tests, do not run on Node 20, which made the GitHub `test` job fail. `npm run lint` now generates the ts-rs bindings first, as `typecheck` and `test` already did, because ESLint's type-aware rules need them and they are not committed.
- 2026-09-19 — The built-in packaging rules (used when a plugin has no `.distignore`) now leave out every hidden file and folder (`.*`), plus `/docs`, `/bin`, `pnpm-lock.yaml`, `psalm.xml`, `rector.php`, `babel.config.*`, `jest.config.*`, `Gruntfile.js`, `gulpfile.js`, `Makefile`, `CODE_OF_CONDUCT.md` and `*.tar.gz`. A developer's real plugin shipped a hidden `.agent/` folder under the old list. `/build` and `/dist` stay in the list, but are kept when the plugin's PHP or a `block.json` refers to them: leaving out a block plugin's `build/` would publish a broken plugin, and shipping an extra folder only costs size.
- 2026-09-19 — Step 5 pauses for a file check (phase `AwaitingFileReview`) when the plugin has no `.distignore`, on the first release (trunk is empty), or when top-level files or folders are not in trunk yet. It shows what will be released and left out, and lets the developer edit the rules with a live preview. With no `.distignore`, SVNpush proposes one built from the built-in rules and saves it on confirm. The file stays after a dry run or a cancel, because it is the developer's saved choice. Otherwise the release does not pause, so routine releases stay one click. When a pre-build command creates the package root, the rules are not editable there.
- 2026-09-19 — V11 also blocks files that hold secrets, whatever `.distignore` says: `.env*`, `wp-config.php`, `*.pem`, `*.key`, `*.p12`, `*.pfx` and SSH private keys (`id_rsa*`, `id_ed25519*`). Publishing one to the public WordPress.org repository cannot be undone.
- 2026-09-19 — The engine integration tests are split into `run_integration.rs` (the release flow) and `run_features.rs` (AI, assets-only, file check), with shared helpers in `tests/support/`, to keep each file under 500 lines.
- 2026-09-19 — Subversion setup is guided, not bundled. The first launch opens a new sixth screen, Help, with a setup checklist: Subversion, SVN account, AI provider (optional) and first plugin, each with a button to fix it. **Install Subversion** runs `winget install --id Slik.Subversion --exact --source winget` on Windows (the Apache-2.0 command-line tools, installed to a folder SVNpush already searches) or `brew install subversion` on macOS, after showing the command. Where neither exists it shows the command to run. The Linux `.deb` and `.rpm` depend on `subversion`. SVNpush never asks for an administrator password itself. Bundling svn was rejected: it would mean building and security-patching it for three platforms. Rewriting SVN was rejected: it would replace the most proven part of a release with new code. A release that finds no Subversion offers **Open Help**. `setup_seen` in settings makes the first-launch redirect happen once.
- 2026-09-19 — The Help screen's copy lives in `helpStrings.ts`, reached as `S.help`, because adding it to `strings.ts` would push that file over 500 lines. `S` stays the single entry point for every string.
- 2026-09-19 — The WordPress.org readme validator is reimplemented locally, instead of posting the readme to WordPress.org's page, which has no API and is a form meant for people. The rules, limits and messages follow the official `class-validator.php` and `class-parser.php` in the WordPress/wordpress.org repository: a 150-character short description; 2,500 words per section (5,000 for Changelog and FAQ); 5 tags, ignoring `plugin` and `wordpress`; the version-field patterns; the licence lists; and the plugin-name header rules. Version fields above the current WordPress branch plus 0.1 are flagged, compared by major.minor. Three official checks need WordPress.org's data (trademarked names, whether contributor usernames exist, tag usage counts). They are left to the official page, which the app links to. Validator errors are blocking check V17, validator warnings are warning W11, and notes are shown only in the readme check.
- 2026-09-19 — **Check readme.txt** and **Build package** are cards on the project page and work without a release. Build package runs the pre-build command and the same packaging rules and package checks as Step 5, holding the project lock, and writes only to SVNpush's build folder, never into the plugin. The developer's own `dist/` build keeps working through the package-root and pre-build settings. The card copy lives in `toolStrings.ts` (`S.tools`), like `S.help`, to keep `strings.ts` under 500 lines.
- 2026-09-19 — Plugin images are checked against the WordPress.org plugin-assets handbook:
  - **Names and sizes:** `icon-128x128` and `icon-256x256` (PNG, JPG or GIF, up to 1 MB); `icon.svg`, which needs PNG fallbacks; `banner-772x250` and `banner-1544x500` (PNG or JPG, up to 4 MB), with `-rtl` or language suffixes; `screenshot-N` (PNG or JPG, up to 10 MB), with language suffixes; the `blueprints/` folder.
  - **Pixel sizes** are read from PNG, JPEG and GIF headers in about 40 lines, instead of adding an image crate.
  - **Wrong entries**, meaning wrong names, sizes, uppercase letters, `.jpeg`, unreadable images or oversized files, are warning W12. W12 is built by the run (it reads files) and appended to Verify, including in assets-only runs.
  - **The Plugin images card** lists each file with its role and size, suggests a missing icon, banner or screenshots, and can create the folder. Help has the same size guide.
- 2026-09-19 — The assets folder keeps the name `.wordpress-org`. It is the convention WordPress developers and tools already use (the 10up deploy action's default), so renaming it would break existing plugins and surprise experienced developers.
